# 선린밸리 커스텀 시스템 통합 구현 계획

> 2026-10-26 승인 당시 계획입니다. 구현·검증 결과와 남은 운영 확인은 [현재 현황](../../custom-systems-status.md)을 참고하세요. 운영 채널 전환·실서버/AWS 적용·발행은 별도입니다.
> 기존 개발 체크아웃에서 구현합니다. 별도 서버/클라이언트 복사본으로 검증하고 실제 운영 데이터는 보존합니다.

**목표:** 기존 Society: Sunlit Valley 모드를 우선 활용해 선린밸리 전용 상자 2종, 안전한 보상 지급, 개봉 GUI, 이용권 동작과 관리 기능을 연결합니다.

**구조:** 보상 정책·확률·접속 보상·건피권은 KubeJS/JSON이 담당합니다. Sunrin Core는 실제 Forge 화면·애니메이션·통신·칭호·이름 색상 동기화·관리자 패널과 검증상 꼭 필요한 최소 저장 브리지만 담당합니다. 경제·상점·퀘스트·토지 보호는 해당 기존 모드를 활용합니다.

**환경:** Society: Sunlit Valley 4.1.5A / Minecraft 1.20.1 / Forge 47.4.0 / Java 17. 현재 운영 구성 0.1.4, 런처 1.1.3.

**요구사항 근거:** 2026-10-26 첨부 `Random Box & Gacha UI Implementation`의 공통 UI·배포·보안 요구, 후속 `Random Box Reward Pool — Revised Requirements`, 사용자 답변의 StageBox→Beat Lamp·원본 주머니 지급·이용권 동작 연결·파티 청크·건피권 채팅 TP 지시와 후속 칭호권/이름 색상 변경권·똥 0.01%·전체 가구 풀 수정. 서로 다른 경우 이 문서의 최종 확정사항을 적용합니다.

### 기존 시스템의 실제 한계

- FTB Quests의 StatTask는 개인의 절대 누적 통계를 **팀 진행도**에 반영합니다. 단순 반복 `play_time` 퀘스트로 30분 보상을 만들면 초기 기준을 넘긴 뒤 즉시 재완료될 수 있으므로 개인 반복 보상용으로 사용하지 않습니다.
- `player.give()`와 원본 주머니 개봉은 공간이 없으면 드롭할 수 있습니다. 이를 안전한 우편함/인벤토리 직배송으로 가정하지 않습니다.
- `persistentData`는 저장 수단이지만, 그것만 사용했다는 이유로 강제 크래시에도 정확히 한 번 지급을 보장한다고 선언하지 않습니다.
- Easy NPC의 별도 Configuration UI가 현재 포함됐다고 확인되지는 않았습니다. 원본 대화·상점 데이터 연결을 우선하고, 제공되지 않은 편집 GUI나 완성형 직업 레벨 기능을 약속하지 않습니다.

## 3. 일반 랜덤박스 보상표

항상 아래 중 **아이템 1개**를 서버에서 결정합니다. 모자 주머니는 원본 아이템이며, 똥은 해당 보상 스택에만 이름·설명을 붙인 갈색 염료입니다. 가중치 단위는 10,000이며 합계 검증으로 실수 반올림에 따른 확률 변형을 피합니다.

| 보상 | 실제 아이템 ID | 확률 | 가중치 |
|---|---|---:|---:|
| 일반 모자 주머니 | `simplehats:hatbag_common` | 38.99% | 3899 |
| 고급 모자 주머니 | `simplehats:hatbag_uncommon` | 27% | 2700 |
| 희귀 모자 주머니 | `simplehats:hatbag_rare` | 12% | 1200 |
| 영웅 모자 주머니 | `simplehats:hatbag_epic` | 3% | 300 |
| 시즌 주머니 전체 | 아래 실제 시즌 주머니 4종 각각 1% | 4% | 400 |
| 칭호권 | `kubejs:rename_ticket` (기존 ID 유지) | 3% | 300 |
| 닉네임 색상 변경권 | `kubejs:name_color_ticket` (신규) | 2% | 200 |
| 건피권 | `kubejs:geonpi_ticket` | 10% | 1000 |
| 똥 | `minecraft:brown_dye` (보상 스택 이름/설명만 변경) | 0.01% | 1 |
| 합계 | | **100%** | **10000** |

건피권 10%, 칭호권 3%, 닉네임 색상 변경권 2%와 똥 0.01%를 유지합니다. 2026-10-27 사용자 수정에 따라 시즌 주머니는 4종 각각 1%, 합계 4%입니다. 늘어난 3%를 일반 주머니에서 차감해 **38.99%**로 조정하며 전체 합계는 100%입니다.

현재 실제 시즌 주머니는 `simplehats:hatbag_easter`, `simplehats:hatbag_summer`, `simplehats:hatbag_halloween`, `simplehats:hatbag_festive`의 4종입니다. 네 종류를 별도 보상으로 각각 1%씩 지급합니다.

- 서버가 실제 레지스트리에 있는 시즌 4종을 모두 검증합니다. 각 1%를 별도로 표시하고, 한 종류라도 누락되면 상자를 소비하기 전에 차단합니다. 남은 시즌 주머니의 확률을 늘리지 않습니다.
- 시즌 후보가 하나라도 없거나 필수 주머니/이용권이 누락되면 기본 정책은 개봉 차단·아이템 미소비입니다. 다른 범주의 비율을 몰래 늘리거나 무효 아이템/공기를 지급하지 않습니다.
- 운영자가 대체 보상을 쓰려면 데이터에 명시하고 검증을 통과해야 합니다. 기존 진행 중 개봉은 새 설정으로 재추첨하지 않습니다.
- 주머니의 우클릭 동작은 수정하지 않습니다. 원본 SimpleHats는 모자를 서버에서 아이템 엔티티로 드롭합니다.
- 원본 설정 `simplehats-common.toml`의 `seasonalBagChance=0.2`에 따라 행사 중 일반 주머니에서 시즌 주머니가 추가로 나올 수 있습니다. **위 각 1%(합계 4%)는 선린 랜덤박스가 직접 지급하는 항목 확률**이며, 이후 원본 주머니를 여는 단계까지 합친 전체 시즌 획득 확률이 아닙니다. 원본 기능을 유지합니다.

## 4. 가구랜덤박스 — 전체 적격 가구 중 하나

표시 이름은 **가구랜덤박스**, 신규 ID는 **`kubejs:furniture_random_box`**로 통일합니다. 원본 `society:furniture_box`는 유지합니다. 신규 아이템은 아직 등록 전입니다.

전체 조사 후보와 실제 ID는 [가구랜덤박스 후보 목록](../../furniture-random-box-candidates.md)에 정리합니다. 현재 2,338개 후보와 별도 경계 검토 534개이며, 외형·런타임 검증 전 초안입니다. 운영 보상 파일은 아직 만들지 않았습니다.

### 최종 선택 방식

1. 설치된 가구·장식 모드의 실제 가구 아이템을 넓게 수집합니다. 앞서 소개한 소수의 예쁜 가구만 추리는 방식으로 제한하지 않습니다.
2. 실제 레지스트리·원본 팩의 대체 ID/초기화 규칙·정상 사용 가능 여부를 검증합니다.
3. 밋밋한 양털 블록/방석 수준의 기본형과 사용 불가 항목을 명시적인 제외 목록으로 뺍니다.
4. 중복 ID를 제거한 **최종 적격 아이템 목록에서 균등하게 1개**를 선택합니다.

- 가구별 확률을 사전에 고정하지 않습니다. 최종 아이템 수가 N개이면 각 아이템은 1/N입니다. 목록이 변하면 그 값도 자연스럽게 바뀝니다.
- 가구 계열별 가중치·희귀도·20종 제한·계열 선택 후 색상 선택 같은 별도 추첨을 두지 않습니다. 서로 다른 유효 아이템 ID는 최종 목록의 개별 항목입니다.
- 가구 종류를 AI/코드가 ‘예쁨’으로 자동 판단한다고 가정하지 않습니다. 실제 목록/외형 확인으로 기본형 제외 기준을 정하고, 제외 ID와 이유를 데이터로 기록합니다.
- ‘양털을 재료로 사용한다’는 이유만으로 제외하지 않습니다. 디자인에 특징이 있는 천 소파·중세/왕실 가구는 포함하고, 단순 양털/방석 수준의 밋밋한 형태를 제외합니다.
- 대상은 모드의 **가구·장식 아이템**입니다. 해당 모드의 제작 재료·도구·생성 알 등 모든 아이템을 무조건 넣는 것은 아닙니다. 앉기·수납·조명 같은 정상적인 가구 기능은 배제 이유가 아닙니다.
- 중세풍 가구·대형 시계·개구리 조명·장식·개구리 의자 등은 포함 방향의 예시입니다. 최종 개수와 실제 ID는 전체 목록 검증 후 산출합니다.
- 원본이 제작법을 제거해 상자 전용으로 만든 가구를 단지 ‘제작 불가’라는 이유로 제외하지 않습니다. 반면 `adv_` ID나 NBT 초기화가 필요한 항목은 원본 경로를 재사용해야 하며, 잘못된 원본 ID를 무작정 지급하지 않습니다.
- 검증된 전체 목록이 비면 소모 없이 개봉을 거부합니다. 누락/제외된 항목과 최종 목록 수·해시를 남겨 운영자가 구성을 확인할 수 있게 합니다.

### 상점과 지급

- 너무 평범한 기본형은 기존 NPC/상점에서 저렴하게 구입하는 쪽으로 분리합니다. 실제 가격은 운영 설정에서 확정합니다.
- 우클릭 → 서버가 1개 결정 → 상자 1개 소비/결과 기록 → 즉시 지급입니다. 개봉 GUI나 애니메이션을 띄우지 않습니다.
- 인벤토리에 넣고 들어가지 않는 나머지는 발밑에 드롭합니다. 원본 상자의 단계별 2배 보상 처리는 새 상자에 적용하지 않습니다.

## 5. 개봉 처리·GUI·지급 일관성

### 개봉·지급 흐름

1. 서버가 새 상자 ID·수량·실행 플레이어·중복 요청을 확인합니다.
2. KubeJS가 현재 검증된 설정으로 보상 아이템 1개를 한 번 결정합니다.
3. 상자 소비와 보상 확정/전달 상태를 일관되게 기록합니다. 저장 실패 시 개봉 성공을 알리지 않습니다.
4. `player.give(ItemStack)` 계열의 실제 인벤토리 우선/남은 수량 드롭 동작을 사용합니다. 가득 찼다는 이유로 인벤토리 수령 대기함에 넣지 않습니다.
5. 가구랜덤박스는 여기서 끝납니다. 랜덤박스만 거래 ID·이미 지급한 실제 ItemStack·표시 등급·설정 버전을 화면에 전달합니다.
6. 화면은 연출과 결과 표시만 담당합니다. 클릭으로 건너뛰거나 닫아도 결과를 다시 뽑거나 아이템을 다시 지급하지 않습니다.
7. ‘한 번 더 열기’와 연속 개봉의 다음 회차는 서버의 새 상자 소유 검증을 거치는 별도 거래입니다.

### 랜덤박스 GUI 사양

- 어두워진 배경과 선린밸리의 따뜻한 색감, 중앙 패널·상자 애니메이션.
- 보상 아이콘 카루셀 → 부드러운 감속 → 당첨 아이템 강조 → 결과 화면.
- **연출 중 좌클릭 한 번으로 같은 확정 결과를 즉시 표시**합니다. 그 클릭이 다음 상자 개봉까지 동시에 실행되지 않게 상태와 입력을 분리합니다.
- 원본 주머니·이용권·커스텀 표시된 갈색 염료의 **실제 아이콘·이름·수량**을 표시합니다. 주머니 보상을 모자 당첨처럼 표현하지 않습니다.
- 등급별 색·광택·절제된 입자와 Minecraft 효과음을 사용합니다. 프레임 시간 기반 보간으로 처리합니다.
- 닫기·한 번 더·확률 보기·소유 상자 수량·지급 완료 상태를 제공합니다. 인벤토리 부족용 수령 대기 UI는 두지 않습니다.
- **연속 열기 ON/OFF**를 제공합니다. 한 회차의 확정 결과를 보여준 뒤 다음 상자 1개를 서버에 요청합니다. 여러 개를 한꺼번에 미리 소비하지 않습니다.
- 상자 소진·사용자 중지·화면 닫기·접속 종료·서버 오류 시 연속 열기를 멈춥니다. 이미 확정/지급한 보상은 유지합니다.
- 인벤토리가 가득 찼어도 요청한 정책대로 바닥 지급하며 연속 열기를 계속할 수 있습니다.
- 한글, 16:9/16:10, 여러 GUI 배율 검증. 최종 화면에 디버그/플레이스홀더를 남기지 않습니다.

### 똥 0.01% — 금빛 가짜 잭팟 반전

- 똥이 당첨되면 일반 보상 연출을 쓰지 않고, 금빛 광택/빛기둥·입자·과장된 팡파르·극적인 뜸들이기로 엄청난 보상을 기대하게 합니다. 과도한 깜빡임은 피합니다.
- 마지막에 실제 갈색 염료 아이콘과 큰 이름 **‘똥’**을 공개합니다. 금빛 연출은 화면 효과일 뿐, 서버에서 처음 확정한 보상은 끝까지 똥 1개입니다.
- 클릭 스킵은 유지합니다. 건너뛰면 같은 똥 결과 카드로 즉시 이동하며 재추첨·추가 지급·강제 대기를 만들지 않습니다.
- 똥 이름/로어는 당첨된 ItemStack에만 부여합니다. `minecraft:brown_dye` 전체 번역이나 다른 갈색 염료를 바꾸지 않습니다.
- 원본 확률은 0.01%입니다. 테스트 환경에서 당첨 연출을 재현할 수 있게 검사하되 운영 확률을 높여 검증했다고 하지 않습니다.

### 실제 API 확인과 영속 상태

- 고정 KubeJS 2001.6.5-build.16의 `PlayerKJS.give`는 `ItemHandlerUtils.giveItemToPlayer`를 통해 메인 인벤토리에 넣고 남은 수량만 서버에서 ItemEntity로 드롭합니다. 실제 JAR 코드로 확인했으며 현재 새 상자 기능을 인게임 구현/검증했다는 뜻은 아닙니다.
- 원본 SimpleHats 주머니를 나중에 여는 동작은 해당 모드가 원래 처리하는 별도 개봉입니다. 선린 랜덤박스는 원본 주머니를 지급하는 단계만 담당합니다.
- 인벤토리 부족용 보관 큐는 없지만 UUID·고유 거래 ID·확정 결과·설정 버전·전달/완료·보상 회차 기록은 유지합니다. 접속 종료·저장 실패로 미완료된 거래의 복구 기록은 일반적인 인벤토리 부족과 구분합니다.
- KubeJS는 확률과 지급 정책을 유지합니다. Core에 동일한 확률표·뽑기 엔진·경제 시스템을 또 만들지 않습니다.
- 플레이어 인벤토리와 바닥 엔티티는 저장 경계가 다릅니다. 일반 드롭 함수를 호출했다는 이유로 강제 종료까지 중복/유실이 해결됐다고 선언하지 않습니다. 저장 순서·재시작·드롭 엔티티 추적/회수의 장애 지점 테스트를 수행합니다.
- KubeJS만으로 필요한 일관성 검증을 만족시키지 못하면 저장·중복 방지·전달만 담당하는 최소 Core 브리지를 추가합니다. 클라이언트의 결과 확인/스킵을 지급 근거로 쓰지 않습니다.
- 설정 재로드 중인 개봉은 거래에 저장한 결과/버전을 유지합니다. 무효 설정은 마지막 검증본을 유지하거나 새 개봉만 차단합니다.

## 6. 최초 접속·온라인 시간 보상

| 조건 | 랜덤박스 | 가구랜덤박스 |
|---|---:|---:|
| 플레이어별 최초 지급 1회 | 15개 | 15개 |
| 실제 온라인 시간 누적 30분마다 | 5개 | 5개 |

- UUID별 기록으로 처리합니다. 팀 퀘스트 진행도와 분리합니다.
- 실제 온라인 세션의 경과 시간만 합산합니다. 로그인·재시작 시 세션 기준을 다시 잡아 오프라인 기간을 계산하지 않습니다.
- 실제 API `Utils.getSystemTime()`은 시스템 시각이므로 시계 역행/급변을 방어합니다. `player.stats.playTime`은 틱 통계라 서버 렉 시 현실 30분과 차이가 있음을 구분합니다.
- 기본 해석은 접속 중 시간이며 별도 AFK 제외 기능을 추가한다고 가정하지 않습니다.
- 누적 시간·지급된 회차·전달 상태를 함께 보존합니다. 보상도 인벤토리 우선/남은 수량 드롭 정책을 사용하며 재접속으로 같은 회차를 중복 지급하지 않게 합니다.
- 제안 기본 정책: 기존 플레이어도 기능 도입 뒤 최초 지급을 1회 받되, 도입 이전 플레이 시간의 소급 보상은 하지 않습니다. 기존 통계를 초기화하지 않고 별도 기준점으로 구분합니다. 이 두 도입 정책은 구현 착수 때 확인합니다.

## 7. 이용권과 관리자 기능

### 칭호권 — 기존 닉변권 전환

- 기존 `kubejs:rename_ticket` ID와 리소스 경로를 보존하고 표시명/동작을 **칭호권**으로 바꿉니다. 기존 보유 이용권도 같은 ID로 남습니다.
- Minecraft 프로필 이름을 바꾸지 않고 **이름 앞에 칭호**를 붙입니다. 닉네임 별칭 교체 기능은 만들지 않습니다.
- GUI에서 칭호 본문, 미리 제공한 태그 형식(예: `[칭호]`, `<칭호>`, `【칭호】`), 칭호 색상을 선택하고 실제 적용 모습을 미리 봅니다.
- 칭호 본문은 **1~10글자**입니다. 자동으로 붙이는 괄호는 글자수에서 제외합니다. GUI와 서버가 동일한 Unicode 문자 단위/정규화 기준을 사용하며, 한글·결합문자·이모지 경계를 테스트합니다.
- 칭호 본문·괄호 형식·칭호 색상을 한 번에 적용합니다. 서버 검증과 영구 저장/동기화가 성공한 뒤 이용권 1개를 소비합니다. 취소/실패는 소비하지 않습니다.
- 표시 문자열은 리터럴 컴포넌트로 만듭니다. 제어문자·줄바꿈·직접 입력 포맷 코드는 검증하고, 색/괄호는 허용된 선택값으로 처리합니다. 같은 칭호를 다른 플레이어가 쓰는 것을 닉네임 중복처럼 막지 않습니다.

### 닉네임 색상 변경권 — 신규 아이템

- 새 `kubejs:name_color_ticket`을 등록하고 표시명은 **닉네임 색상 변경권**으로 합니다.
- 전용 GUI의 색상 선택/미리보기로 **원래 Minecraft 프로필 이름의 색상만** 바꿉니다. 칭호 본문·괄호·칭호 색상은 건드리지 않습니다.
- 색상 선택은 읽기 쉬운 기본 팔레트를 제공하고, 검증된 색상을 서버가 저장/동기화한 뒤 이용권 1개를 소비합니다.
- 색상 변경을 위해 플레이어를 새 scoreboard 팀에 강제로 넣지 않습니다. 기존 FTB 파티·팀 접두어·토지 보호는 유지합니다.

### 표시 프로필 공통 처리

- UUID별로 `titleText`, `titleStyle`, `titleColor`, `nameColor`를 독립적으로 저장합니다. 실제 Minecraft 프로필 이름/인증 UUID와 Microsoft 계정을 변경하지 않습니다.
- 칭호 앞부분과 이름 부분의 색을 각각 적용한 컴포넌트를 구성하고 채팅·탭·이름표·재접속·차원 이동·다른 플레이어의 화면에 동기화합니다.
- Forge `NameFormat`, `TabListNameFormat` 및 고정 버전의 이름 갱신 API를 기반으로 합니다. 기존 팀 접두어·색, Chat Heads, 채팅 서명 계층을 함께 검증합니다.
- 싱글플레이 통합 서버와 전용 서버 모두 서버가 프로필 적용/이용권 소비를 결정합니다.

### 건피권 — KubeJS 채팅 버튼 방식

이 흐름은 실제 KubeJS 6의 `.clickRunCommand`, `ServerEvents.commandRegistry`, 플레이어별 메시지·차원 이동 API로 구현할 수 있습니다.

```text
[칭호] peach_min님이 건피권을 사용하셨습니다. [이동하기]

운영자 이동 후: 호출자 위치로 이동했습니다. [복귀하기]
```

- 새 요청/수락 GUI 없이 지정된 온라인 운영자 UUID에게만 메시지를 보냅니다.
- 제안 기본값: 호출 알림을 정상 전달한 시점에 1개 소비하고, 온라인 운영자가 없으면 소비하지 않습니다.
- 버튼은 `/sunrin geonpi go <token>` 같은 고정 명령을 실행합니다. 칭호·이름 같은 표시 문자열이나 사용자 입력 좌표를 명령 문자열에 넣지 않습니다.
- 서버는 매 실행마다 운영자 UUID와 호출 토큰을 검증합니다. 토큰 복사·명령 직접 입력으로 권한을 얻지 못하며 TP를 위해 OP를 부여하지 않습니다.
- 이동 직전 운영자의 차원·좌표·시선을 저장하고, 버튼을 누른 시점의 호출자 위치로 이동합니다. 호출자가 나간 경우 안내하고 이동하지 않습니다.
- `[복귀하기]`는 본인 저장점으로 이동하며 성공한 뒤에만 기록을 지웁니다. 복귀 실패 시 기록을 보존합니다.
- 재클릭으로 복귀점을 덮어쓰지 않습니다. 제안 기본값은 복귀 전 다른 호출 이동을 막고 기존 복귀점을 지키는 것입니다.
- 토큰 만료·차원 부재·위험한 도착 지형·순간이동 실패를 처리합니다. 기본 `teleportTo`가 안전 지형까지 보장한다고 가정하지 않습니다.
- Core의 표시 프로필(칭호·이름 색상) 조회 브리지만 재사용합니다. 인증된 Minecraft 계정명을 기준으로 알리고, 표시 문자열을 파싱해 신원을 추측하지 않습니다. 건피권의 알림·이동·복귀 동작은 사용자 확인대로 유지하고 설명/표시만 갱신합니다.

### 관리자 패널 — 최소 Core 필요

- 서버 측 UUID 허용 목록으로 접근·개별 동작을 검사합니다. OP 여부와 별개로 패널에 접근할 수 있습니다.
- OP ON/OFF와 Survival/Creative/Spectator는 서로 독립된 동작입니다. 기존 서버 명령/API를 호출하며 권한 엔진을 새로 만들지 않습니다.
- 전용 명령/패킷은 허용한 동작만 선택하게 하고 임의 명령 문자열을 받지 않습니다.
- Core가 임시로 부여한 OP는 부여 전 원상태·회수 의도를 영속 기록합니다. 재접속·서버 재시작/비정상 종료 복구 시 Core 소유 변경만 정리하고 기존 외부 OP 설정은 보존합니다.
- 운영자 UUID 목록은 구현 전에 입력합니다. 테스트 UUID가 운영 설정으로 남지 않게 합니다.

| 닉네임 색상 변경권 | 화려한 닉이 나를 감싸네 |
| 똥 | 꽝입니다. 확률이 0.01%인 |

마지막 로어의 ‘인’까지 현재 요청 문자열로 보존합니다. 일반 갈색 염료 전체의 이름/설명을 수정하지 않습니다. 선린 급식의 기존 이름·설명·수치는 그대로 유지합니다.

## 8. 토지·경제·NPC·퀘스트

### 토지 보호

- FTB Chunks의 `max_claimed_chunks: 4`, `party_limit_mode: "sum"` 방향으로 적용합니다. 파티 전체를 4로 제한하는 설정은 사용하지 않습니다.
- 기존 월드의 `serverconfig/ftbchunks-world.snbt`를 백업하고 필요한 키만 병합합니다. `defaultconfigs`만 바꾸고 기존 월드에 적용됐다고 하지 않습니다.
- 기존 초과 점유를 자동 해제하거나 플레이어 토지를 초기화하지 않습니다.
- 퀘스트/보호 해금 시점은 보류이며 원본 진행 조건은 당장 덮어쓰지 않습니다.

### 경제와 NPC

- 기존 Numismatics 은행과 `getPersonalOrCurioAccount`/입출금 헬퍼를 재사용합니다.
- 기존 Easy NPC 엔티티 + SVDialog + Society Trading의 연결을 이어 쓰고, 고유 Sunrin 상점/대화 ID와 JSON으로 확장합니다.
- 상점의 `offer`, `request`, `numismatics_cost`, 단계·계절 조건 등 기존 데이터 구조를 사용합니다. 가격은 설정 데이터로 관리하고 미확정 가격을 임의로 운영에 적용하지 않습니다.
- 직업은 기존 대화·상점·단계 조건으로 가능한 범위부터 연결합니다. 완성형 직업 레벨/급여 시스템이 이미 있다고 가정하지 않습니다.
- 퀘스트는 현재 모드를 유지하고 재설계·신규 퀘스트/보상 흐름 적용은 별도 단계로 보류합니다.

### 단계 1 — 모드 교체와 배포 기반

## 12. 검증의 우선순위

1. 박스 소비·보상 기록·인벤토리의 저장 경계에서 강제 종료해도 중복/유실이 없는지.
2. 신규 상자와 원본 상자의 이벤트가 섞여 2중 보상이 발생하지 않는지.
3. 시즌 후보 누락·설정 오류가 표시 확률과 실제 확률을 어긋나게 하지 않는지. 똥 0.01%/일반 38.99%의 합계와 보상 스택 이름/로어가 맞는지.
4. 클라이언트 UI·명령 문자열·토큰만으로 서버 권한이나 보상을 결정하지 않는지.
5. StageBox 제거, 신규 Core 및 Beat Lamp의 양쪽 버전 일치와 월드 보존.

이 문서는 계획이며 위 완료 조건의 기능 테스트를 이미 실행했다는 뜻이 아닙니다.

## 13. 구현 착수 때 남은 운영 값
